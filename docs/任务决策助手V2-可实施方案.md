# Codemini 任务决策助手 V2 可实施方案

## 1. 目标

把当前“继续、重试、询问、升级、完成”的判断层，升级为覆盖任务路径、Skill、工具、子代理、上下文、工具护栏和完成度复核的完整决策系统。

目标分工：

- **模型端**：理解任务、生成计划、执行工具、编写代码、生成总结；
- **Jev/Laya**：在有限候选中做结构化选择、评分和真假判断；
- **Codemini 策略层**：过滤候选、执行权限和风险检查、处理审批、决定是否接受 provider 建议；
- **审计层**：记录状态、候选、概率、策略覆盖和最终结果，支持回放与反事实评估。

Jev/Laya 不直接执行工具。这个边界符合 Jev 的工具护栏设计：provider 返回决策，宿主应用负责策略和执行。[Jev API 文档](https://www.jevai.org/docs)

## 2. 最终运行链路

```text
用户任务
  ↓
状态收集器
  ├─ 任务目标和验收标准
  ├─ 当前 Agent 阶段
  ├─ 可用工具和 Skill
  ├─ 权限、沙箱、风险和审批状态
  ├─ 历史成功率、失败原因和冷却状态
  └─ 最近测试、diff 和工具结果
  ↓
候选过滤器（Codemini 确定性代码）
  ↓
Jev/Laya 并行决策
  ├─ task_route
  ├─ skill_route
  ├─ tool_route
  ├─ tool_guard
  ├─ context_keep
  ├─ subagent_route
  └─ completion_review
  ↓
策略门禁（Codemini 确定性代码）
  ├─ allow
  ├─ confirm
  ├─ review
  ├─ fallback
  └─ deny
  ↓
模型执行工具或 Skill
  ↓
结果分类、可靠性更新、审计和下一轮决策
```

Jev 官方推荐的基本模式也是“收集状态 → 决策 → 应用策略 → 宿主执行并记录回执”。[JevRouter 工作方式](https://www.jevrouter.co/how-it-works)

## 3. 决策协议

### 3.1 统一请求

新增 `src/core/harness/decision-protocol.js`：

```js
{
  decisionId: "uuid",
  episodeId: "session:turn",
  step: 4,
  kind: "tool_route",
  state: {
    objective: "修复登录接口并补测试",
    stage: "implement",
    evidence: [],
    constraints: [],
    riskTier: "low"
  },
  candidates: [
    {
      id: "run",
      type: "tool",
      description: "运行工作区命令",
      allowed: true,
      reliability: 0.86,
      sideEffects: ["可能修改文件"],
      reversibility: "partially_reversible"
    }
  ],
  questions: [
    {
      id: "selected_tool",
      type: "choice",
      options: ["run", "rg", "skill", "ask_user", "none"],
      criteria: {}
    },
    {
      id: "needs_review",
      type: "noul"
    },
    {
      id: "risk",
      type: "score",
      levels: ["low", "medium", "high", "critical"]
    }
  ],
  policyVersion: "tool-route-v1"
}
```

问题必须保持单一、答案范围必须明确。Choice、Score、Noul 分别用于选择、等级评分和真假概率。[Jev AI GitHub](https://github.com/jev-ai)

```js

  answers: [
    {
      id: "selected_tool",
      type: "choice",
      choice: "run",
      probabilities: {
        run: 0.72,

        skill: 0.08,

  optionsHash: "sha256:..."

```

## 4. 七个决策点

### 4.1 `task_route`

候选：

- `proceed_fast`
- `deep_review`
- `split_task`
- `ask_user`
- `block`

触发时机：新任务开始、需求明显变化、连续失败两次、风险等级升高。

策略：高风险任务不能进入 `proceed_fast`；低置信度进入 `ask_user` 或 `deep_review`。

### 4.2 `skill_route`

候选来自当前真实可用 Skill：

- Skill 名称；
- 一句话用途；
- 适用阶段；
- 最近成功率；
- 是否需要额外权限；
- `none`。

策略：先由 Codemini 过滤被禁用、缺失或权限不满足的 Skill，再调用 Jev。Jev 只从候选中选择。

### 4.3 `tool_route`

候选来自 `toolRuntime.definitions()`，但在发给 Jev 前移除：

- 当前阶段不可用的工具；
- 权限不满足的工具；
- 高风险但没有审批的工具；
- 处于冷却期的工具；
- Schema 不完整的工具；
- 最近连续失败且没有备用理由的工具。

每个候选附带可靠性、延迟、成本、失败类别、可逆性和副作用。

策略：选择概率低于 `0.55` 或前两名差距小于 `0.12` 时，回退给模型自由选择或询问用户。

### 4.4 `tool_guard`

每次真实工具执行前调用。

输入：工具名、动作摘要、参数摘要、副作用、可逆性、已有验证和风险策略。

输出：

- `allow`
- `confirm`
- `review`
- `deny`

策略覆盖顺序：

```text
确定性禁止 > 审批要求 > provider guard > 模型计划
```

provider 不能降低 Codemini 的安全限制。

### 4.5 `context_keep`

对每个上下文块询问是否保留：

- 最近测试结果；
- 失败原因；
- 需求和验收标准；
- 当前 diff；
- 工具输出；
- 旧的中间推理。

以下内容永远保留：系统指令、审批结果、沙箱策略、关键验收证据、当前目标。

### 4.6 `subagent_route`

候选：

- `main_agent`
- `research_agent`
- `review_agent`
- `test_agent`
- `docs_agent`
- `ask_user`

策略：高风险或低置信度任务不能自动交给未授权子代理；子代理必须返回 receipt，包括输入状态、动作、工具和结果。

### 4.7 `completion_review`

在最终总结前调用，输入：

- 原始目标；
- 验收标准；
- 已完成工作；
- 测试和验证结果；
- 当前 diff；
- 已知缺口。

输出：

- `complete`
- `verify_more`
- `incomplete`

只有 `complete` 且确定性验证通过，才能把任务标记为完成。Jev 官方 API 已提供类似的完成度判断场景。[Jev API completion](https://www.jevai.org/docs)

## 5. 工具和 Skill 可靠性模型

### 5.1 记录维度

每次使用记录：

- 工具或 Skill 名称；
- 任务类型；
- 项目类型；
- 成功、失败、超时、权限拒绝、参数错误；
- 延迟；
- 是否产生有效结果；
- 是否需要重试；
- 重试是否成功。

### 5.2 可靠性评分

使用带平滑的 Beta 后验：

```text
reliability = (successes + 1) / (successes + failures + 2)
```

失败原因不能全部混在一起：

- 权限错误：降低当前环境可用性，不永久惩罚工具；
- 参数错误：降低当前参数模板的可靠性；
- 超时：增加延迟和临时故障权重；
- 非零退出码：降低当前任务类型下的可靠性；
- 成功但结果无效：降低任务适配度。

### 5.3 冷却策略

建议默认值：

- 连续失败 2 次：可靠性低于 0.45，降低排序权重；
- 连续失败 3 次：进入 5 分钟冷却；
- 权限拒绝：当前会话立即冷却；
- 明确成功一次：解除临时冷却，但不清空历史。

## 6. 数据库改动

新增表：

```sql
CREATE TABLE harness_decision_candidates (
  decision_id TEXT NOT NULL,
  candidate_id TEXT NOT NULL,
  candidate_type TEXT NOT NULL,
  allowed INTEGER NOT NULL,
  probability REAL,
  selected INTEGER NOT NULL DEFAULT 0,
  policy_overridden INTEGER NOT NULL DEFAULT 0,
  override_reason TEXT NOT NULL DEFAULT '',
  PRIMARY KEY(decision_id, candidate_id)
);

CREATE TABLE harness_tool_outcomes (
  id TEXT PRIMARY KEY,
  episode_id TEXT NOT NULL,
  step INTEGER NOT NULL,
  candidate_id TEXT NOT NULL,
  task_kind TEXT NOT NULL DEFAULT '',
  outcome TEXT NOT NULL,
  error_class TEXT NOT NULL DEFAULT '',
  latency_ms INTEGER,
  useful_result INTEGER,
  retry_succeeded INTEGER,
  created_at TEXT NOT NULL
);

CREATE TABLE harness_context_decisions (
  decision_id TEXT NOT NULL,
  context_id TEXT NOT NULL,
  kept INTEGER NOT NULL,
  probability REAL,
  reason TEXT NOT NULL DEFAULT '',
  PRIMARY KEY(decision_id, context_id)
);
```

已有 `harness_episodes` 和 `harness_events` 继续保留，新增表只做查询优化和统计，不改变原始事件回放能力。

## 10. 实施顺序

### Phase A：协议和候选集

- 固化统一请求/响应；
- 从 ToolRuntime 和 SkillRegistry 构建候选；
- 增加候选过滤器；
- 增加完整概率审计；
- 保持 shadow-only。

验收：每次决策都能在回放中看到候选集、概率和版本。

### Phase B：工具路由和工具护栏

- 接入 `tool_route`；
- 接入 `tool_guard`；
- 接入可靠性、冷却和失败分类；
- 对 `run`、文件读写、测试、Skill、MCP、子代理先覆盖。

验收：provider 不可用、低置信度、权限不足和高风险动作都能安全回退。

### Phase C：Skill、子代理和任务路径

- 接入 Skill 路由；
- 接入子代理路由；
- 接入 `task_route`；
- 将选择结果注入模型下一轮上下文。

验收：模型可以看到明确的推荐路径，但不能调用未授权能力。

### Phase D：完成度和上下文

- 接入 `completion_review`；
- 接入上下文保留判断；
- 固定保留安全规则和关键证据。

验收：模型声称完成但验证不足时不会直接结束。

### Phase E：反事实评估和灰度

- 保存候选概率和结果；
- 构建离线反事实回放；
- 统计失败率、人工升级率、重试成功率、延迟、成本；
- 低风险任务 5% 灰度，逐步提升。

验收：每次扩大灰度前都有基于真实结果的校准报告。

## 11. 测试要求

### 单元测试

- 候选过滤；
- 工具可靠性和冷却；
- Choice/Score/Noul 解析；
- 低置信度回退；
- 策略覆盖；
- 工具护栏四种结果；
- 完成度判断；
- 上下文必保留规则。

### 集成测试

- Jev/Laya 超时和错误 Schema；
- provider fallback；
- 权限拒绝不会被 provider 放行；
- 选中的工具必须属于候选集；
- 失败后可靠性下降；
- 成功重试后可靠性恢复；
- 子代理 receipt 完整。

### 端到端测试

- 任务路由 → Skill → 工具 → 测试 → 完成度复核；
- 工具失败 → 换工具 → 成功；
- 高风险工具 → confirm/review；
- 低置信度 → ask_user；
- provider 不可用 → Rules fallback；
- 外部决策接管模式仍受硬门禁约束。

## 12. 成功指标

第一阶段只在低风险任务中衡量：

- 工具首次选择成功率提升；
- 工具重复失败次数下降；
- 无效重试比例下降；
- 过早完成比例下降；
- 人工升级准确率提升；
- 平均任务步数下降；
- 任务完成时间下降；
- provider 延迟和成本可接受；
- 所有高风险动作没有绕过审批。

## 13. 必须坚持的限制

- Jev/Laya 不直接执行工具；
- provider 概率不是授权；
- 候选集必须先由 Codemini 过滤；
- 高风险动作必须经过硬门禁和人工审批；
- 不确定状态必须有 `unknown`、`none` 或 `ask_user` 路径；
- 不发送 API Key、密码和无关隐私数据；
- 运行时失败不能改变安全策略；
- 所有决策都必须可回放、可解释、可校准。
